| 项目 | 内容 |

| 所属项目 | CMCI — Crypto Market Cycle Intelligence |
| 所属阶段 | 第一阶段 |

## 一、开发目标与边界

### 1.1 本次要解决的问题

CMCI 的研究数据来自不同渠道：

- 全球宏观经济数据
- 全球金融市场数据
- BTC 与 Crypto 市场数据
- 链上数据
- ETF、稳定币及资金流数据
- 机构持仓与市场结构数据
- 价格、成交量、波动率和衍生品数据

这些数据存在几个关键差异：

- 更新频率不同：分钟、小时、日、周、月、季度。
- 统计时间不同：数据描述的时间与数据实际发布的时间不同。
- 修订机制不同：部分数据发布后还会进行历史修订。
- 来源不同：API、公开文件、商业数据接口、人工导入。
- 历史覆盖不同：有些数据具有完整历史，有些只有近几年。
- 可用时间不同：数据描述某个历史时点，不代表当时已经能够获取。

因此，本项目不能只建设一张普通的时间序列表。

必须建立能够区分以下维度：

- 数据描述的时间
- 数据发布的时间
- 数据实际可获得的时间
- 数据版本的时间
- 数据用途
- 数据质量

的研究数据管理系统。

### 1.2 本次开发范围

本次开发包括：

- 指标字典管理。
- 数据源管理。
- 原始数据接入和保存。
- 标准化数据存储。
- 历史数据版本管理。
- L5 数据用途分区管理。
- 历史时点数据回放。
- 数据质量检查。
- 数据缺失与异常监测。
- 前视偏差审计支持。
- 数据导出与研究查询接口。
- 操作日志与版本记录。

### 1.3 本次明确不做

本次不开发：

- L6 周期阶段识别模型。
- 牛熊周期预测模型。
- 周期转换检测算法。
- CCE 综合评价模型。
- 资本质量合成算法。
- MTPS、MRE、网格策略接口的实际接入。
- 自动交易和交易信号。
- 完整研究分析平台或复杂可视化系统。

本次允许提供必要的数据管理页面、查询页面和基础图表，但不能把开发资源投入到尚未完成研究定义的模型功能。

## 二、系统总体结构

建议采用以下逻辑结构：

```text
数据源层
  │
  ┌────────────┼────────────┐
  │            │            │
API接入      文件导入      人工录入
  │            │            │
  └────────────┼────────────┘
               │
        原始数据层 Raw / Immutable
               │
           数据标准化
               │
        标准化数据层 Normalized
  ┌──────────┼──────────┐
  │          │          │
指标字典    数据版本    数据质量
  │          │          │
  └──────────┼──────────┘
             │
        研究数据集层
  ┌──────────┼──────────┐
  │          │          │
训练区      识别区      验证区
  │          │          │
  └──────────┼──────────┘
             │
        历史回放引擎
             │
          审计与导出
             │
       CMCI后续研究
```

建议将系统划分为逻辑模块，实际部署可以根据团队技术栈决定，不要求每个模块独立部署成微服务。

## 三、核心功能模块

### 模块 A：指标字典管理

这是整个系统的基础。

每一个指标必须先登记，再允许正式进入标准化数据层。

#### A1. 指标基本信息

每个指标至少包含：

| 字段 | 说明 |
| --- | --- |
| indicator_id | 指标唯一编号 |
| indicator_code | 英文代码，唯一 |
| indicator_name | 指标名称 |
| description | 指标定义 |
| layer | L1–L5 |
| category | 指标分类 |
| sub_category | 二级分类 |
| unit | 数据单位 |
| frequency | 数据频率 |
| timezone | 时区 |
| data_type | 数值、比例、枚举、文本等 |
| source_policy | 允许使用的数据源 |
| update_method | API、文件、人工等 |
| revision_policy | 是否可能修订及修订规则 |
| history_start | 可用历史起始时间 |
| history_end | 可用历史结束时间 |
| quality_policy | 质量检查规则 |
| license_note | 授权与使用限制 |
| status | 候选、启用、停用 |
| created_at | 创建时间 |
| updated_at | 更新时间 |
| version | 指标定义版本 |

#### A2. 数据用途定义

对于 L5 指标，必须增加：

- usage_partition_policy
- partition_scope
- partition_notes

其中：

usage_partition_policy 用来登记该指标允许参与哪些用途，以及是否需要按研究任务独立分区。

实际进入研究数据集的 L5 观测记录，还必须具备：

usage_partition

允许值：

- training
- identification
- validation

注意：用途分区不是简单地给某个指标永久贴一个标签。同一指标可能在不同研究任务中承担不同用途。

因此建议采用两级管理：

1. 指标字典登记用途政策。
2. 研究数据集中的每条观测记录，或者其明确关联的数据集成员记录，登记实际用途分区。

同一研究任务中，不得因为同一个指标被多个模块读取，就自动获得跨分区使用的权限。

L1–L4 不要求使用 L5 的三分区标签，但也必须记录其在具体研究任务中的使用范围和数据集版本。

### 模块 B：数据源管理

建立统一的数据源登记表。

字段建议：

| 字段 | 说明 |
| --- | --- |
| source_id | 数据源唯一编号 |
| source_name | 数据源名称 |
| provider | 提供机构或服务商 |
| source_type | API、公开数据、商业接口、文件等 |
| base_url | 接口地址或来源页面 |
| access_method | 获取方式 |
| auth_type | 认证方式 |
| license_type | 授权类型 |
| update_frequency | 更新频率 |
| historical_coverage | 历史覆盖范围 |
| revision_support | 是否提供历史版本 |
| reliability_grade | 来源可靠性等级 |
| status | 启用、停用、待评估 |
| notes | 说明 |

要求：

- 一个指标可以对应多个数据源。
- 一个数据源可以提供多个指标。
- 必须能够记录主数据源与备用数据源。
- 不同来源的数据不得未经规则确认直接混合。
- 来源切换必须保留记录。

第一阶段不要求团队一开始就接入所有数据源。先建立数据源登记、接入规范和通用导入能力，再按研究价值逐个接入。

### 模块 C：原始数据层

原始数据层负责保存从外部获得的数据。

核心原则：

原始数据只追加，不原地修改。

每次接入的数据都应保存：

- 原始响应或原始文件。
- 数据源。
- 接收时间。
- 数据源发布时间（如可获得）。
- 数据批次编号。
- 原始内容哈希。
- 接入任务编号。
- 接入状态。
- 错误信息。

建议字段：

| 字段 | 说明 |
| --- | --- |
| raw_record_id | 原始记录编号 |
| source_id | 来源编号 |
| indicator_id | 指标编号 |
| batch_id | 导入批次 |
| received_at | 系统接收时间 |
| source_release_time | 来源发布时间 |
| payload | 原始数据内容 |
| content_hash | 内容哈希 |
| ingestion_status | 接入状态 |
| error_message | 错误信息 |

原始数据发生重复接入时，应识别重复记录，但不得简单覆盖旧记录。

如果来源后来修正了数据，应保存新版本并与旧版本建立关联。

### 模块 D：标准化数据层

将不同来源的数据转换为统一的数据结构。

每条标准化观测至少包含：

| 字段 | 说明 |
| --- | --- |
| observation_id | 观测记录编号 |
| indicator_id | 指标编号 |
| observation_period | 数据描述的观察时间或区间 |
| release_time | 来源发布该数据的时间 |
| available_time | 系统实际能够获得该数据的时间 |
| vintage_time | 数据版本或修订版本时间 |
| value | 标准化后的值 |
| source_id | 数据来源 |
| raw_record_id | 对应原始数据记录 |
| unit | 单位 |
| timezone | 时区 |
| quality_status | 质量状态 |
| revision_id | 修订版本编号 |
| created_at | 系统写入时间 |

对于 L5 数据，必须同时记录对应的研究数据集用途分区。

#### D1. 时间字段规则

必须严格区分：

- observation_period：数据描述的时间。
- release_time：数据发布的时间。
- available_time：CMCI 系统实际能够取得该数据的时间。
- vintage_time：该数据版本形成或发布的时间。

历史回放必须依据 available_time 判断某个时点是否可用。

如果某个宏观数据在历史上被修订：

- 旧版本保留。
- 新版本追加。
- 不得覆盖旧版本。
- 可以查询当前最新版本。
- 也必须能够查询某个历史时点当时可用的版本。

如果来源没有提供准确的历史发布时间或 vintage 信息，必须标记时间信息质量，不得自行假定。

#### D2. 已知未来事件

支持登记已知未来事件，例如 BTC 减半区块高度及其预计时间。

至少增加：

- known_future_event
- event_type
- event_known_time
- event_effective_time
- event_source

此类事件必须与未来市场结果数据区分。

## 四、研究数据集与 L5 三分区管理

这是本系统最重要的约束之一。

### 4.1 研究数据集

建立研究数据集实体：

- dataset_id
- dataset_name
- research_id
- dataset_version
- time_start
- time_end
- created_at
- created_by
- status
- description

研究数据集可以引用多个指标和多个时间序列。

### 4.2 分区登记

建立数据集成员关系：

- dataset_id
- indicator_id
- usage_partition
- time_start
- time_end
- embargo_before
- embargo_after
- partition_version
- created_at

如果需要更精细的控制，可以按时间段登记分区，而不是简单地按指标整体划分。

### 4.3 分区校验

系统必须提供自动校验能力：

- 同一研究任务的识别区和验证区不得存在重叠的同指标同时间窗口。
- 对相邻或重叠窗口，根据预先登记的隔离期执行 embargo 校验。
- 验证区一旦标记为正式验证并完成正式评价，不得被静默改回训练区。
- 如果确实需要重新使用验证区，必须创建新的研究实验版本，明确原验证集已经失去独立验证资格。
- 所有分区变更都要留痕。

研究数据集必须保存分区版本，不能只保存当前分区状态。

### 4.4 L6 隔离

当前系统不开发 L6，但数据模型必须预留研究用途登记。

未来 L6 的周期识别数据集与 L1–L4 驱动力检验数据集必须能够独立登记、独立查询和独立审计。

系统应能够检查：

- 是否使用了相同时间窗口。
- 是否使用了相同 L5 指标。
- 是否发生了识别区和验证区重叠。
- 是否将事后阶段标签当作实时可得输入。

## 五、数据接入与更新

### 5.1 接入方式

第一阶段至少支持：

- API 接入。
- CSV 文件导入。
- Excel 文件导入。
- JSON 文件导入。
- 必要的人工补录。

不要求所有数据源都使用同一种接入方式。

### 5.2 接入流程

```text
创建数据源
  ↓
登记指标
  ↓
配置数据映射
  ↓
执行数据接入
  ↓
保存原始数据
  ↓
数据标准化
  ↓
时间字段校验
  ↓
质量检查
  ↓
写入标准化数据层
  ↓
生成接入报告
```

### 5.3 接入任务管理

每次数据接入必须有独立任务记录：

- job_id
- source_id
- indicator_id
- start_time
- end_time
- execution_time
- records_received
- records_inserted
- records_updated（仅指追加新版本，不是覆盖）
- records_rejected
- job_status
- error_log

### 5.4 更新策略

不同指标应允许配置不同更新策略：

- 实时或高频更新。
- 定时更新。
- 来源发布后更新。
- 手动更新。
- 文件批量更新。

更新频率由数据源能力和指标实际频率决定。

不能为了让系统看起来持续更新，就反复写入没有新信息的旧数据。

## 六、历史数据回放引擎

这是 CMCI 数据基础设施的核心能力。

### 6.1 目标

给定一个历史时间点 T，系统能够还原：

在 T 时刻，CMCI 实际能够获取哪些数据、这些数据当时是什么版本、数据质量如何。

### 6.2 回放逻辑

对于任意指标：

- 只允许使用 available_time <= T 的数据。
- 如果有多个历史版本，只能使用 T 时刻已经可获得的版本。
- 不得使用 T 之后发布的修订数据。
- 不得使用 T 之后才产生的市场结果数据。
- 已知未来事件可以单独读取，但必须具有 known_future_event=true 标记。

### 6.3 回放输出

每次回放生成：

- replay_id
- replay_time
- dataset_id
- dataset_version
- indicator_list
- source_snapshot_id
- revision_id
- available_data_count
- missing_data_list
- quality_summary
- replay_result_hash

### 6.4 回放要求

至少支持：

- 单一历史时点回放。
- 一段历史时间序列回放。
- 指定指标集合回放。
- 指定研究数据集回放。
- 导出回放结果。
- 对比两个历史回放版本。

必须能够证明回放使用的是当时可得的数据，而不是现在看到的最终数据。

## 七、数据质量管理

建立统一的数据质量规则。

### 7.1 基础检查

至少包括：

- 空值检查。
- 重复记录检查。
- 时间顺序检查。
- 数据类型检查。
- 单位检查。
- 极端值检查。
- 数据频率检查。
- 数据中断检查。
- 来源切换检查。
- 历史修订检查。

### 7.2 质量状态

建议采用：

- normal
- warning
- degraded
- unavailable
- unknown

具体判定规则由指标字典配置。

### 7.3 缺失数据

不得静默填补。

如果某个指标缺失：

- 保留缺失状态。
- 记录缺失时间段。
- 记录原因（如已知）。
- 不得默认沿用上一条数值。
- 不得自动把缺失数据当成零。

如研究需要插值，必须在研究处理层显式定义插值方法，并保留原始缺失状态。

### 7.4 数据质量报告

支持按以下维度查看：

- 指标
- 数据源
- 时间区间
- L1–L5 层级
- 研究数据集
- 分区
- 更新任务

## 八、历史记录与 append-only 约束

### 8.1 原始数据

原始数据只追加，不覆盖。

### 8.2 标准化数据

修订和纠错采用追加新版本方式。

### 8.3 研究数据集

数据集定义、指标成员、时间范围、分区和参数发生变化时，创建新版本。

### 8.4 实时推断记录

本阶段暂不开发 L6 实时推断，但底层记录管理必须预留 append-only 机制。

未来实时推断记录一旦写入：

- 不允许原地修改。
- 修正必须追加新记录。
- 新记录关联旧记录。
- 必须保存修正原因。
- 必须保存模型版本和数据快照版本。

### 8.5 删除规则

普通业务用户不得删除历史研究记录。

如因授权、隐私或合规要求必须删除，应采用受控操作，记录操作主体、原因、时间和影响范围。不得以普通数据清理为由破坏研究历史可追溯性。

## 九、前视偏差审计模块

### 9.1 审计目标

验证历史回放和数据处理没有使用历史时点不可获得的信息。

### 9.2 审计流程

1. 创建审计任务。
2. 设定历史时间范围。
3. 设定抽样数量 N。
4. 随机抽取历史回放时点。
5. 对每个时点执行历史回放。
6. 检查所有输入数据的 available_time。
7. 检查 vintage_time 和历史版本。
8. 检查是否存在未来数据或事后修订数据。
9. 输出审计报告。

### 9.3 审计报告

至少包含：

- audit_id
- dataset_id
- dataset_version
- sample_count
- sampled_times
- checked_record_count
- violation_count
- violation_details
- auditor
- audit_time
- audit_result

审计结果：

- passed
- failed
- inconclusive

只要发现无法解释的前视数据使用问题，就不能判定通过。

审计执行者必须独立于数据构建者。开发阶段可先实现审计功能和报告导出，正式验收由独立人员执行。

## 十、查询与导出接口

第一阶段至少提供以下内部接口能力，具体 REST、GraphQL 或其他实现方式由团队决定。

### 10.1 指标查询

按以下条件查询：

- 指标编号
- L1–L5 层级
- 时间范围
- 数据源
- 数据质量状态

### 10.2 数据集查询

按研究数据集、版本、指标和分区查询。

### 10.3 历史回放

传入：

- 历史时点
- 数据集版本
- 指标范围

返回该时点可获得的数据和版本快照。

### 10.4 数据导出

至少支持 CSV、JSON。

导出文件必须包含时间字段、数据来源、版本信息和用途分区，不能只导出一个日期列和一个数值列。

### 10.5 接口版本

接口应具备版本号，避免后续数据结构变化时破坏已有研究脚本。

第一阶段不需要复杂前端，但建议至少提供以下页面。

### 页面 1：指标字典

- 指标详情
- 新增与编辑

### 页面 2：数据源管理

- 数据源列表
- 来源详情
- 接入方式
- 历史覆盖
- 更新时间
- 授权说明
- 接入状态

### 页面 3：数据接入任务

- 任务列表

## 十二、非功能要求

### 12.1 可追溯性

任何标准化数据都必须能够追溯到原始来源和接入批次。

### 12.2 可复现性

同一数据集版本、同一历史时点、同一处理规则，应得到可复现的结果。

### 12.3 可扩展性

允许未来增加：

- 新指标
- 新数据源
- 新数据频率
- 新研究分区
- 新的时间回放规则
- 新的研究模块

不能将指标、来源和层级写死在代码中。

### 12.4 时间精度

统一保存 UTC 时间，同时允许记录来源时区和原始时区。

日期型宏观数据与带时分秒的市场数据，应区分存储和对齐方式。

### 12.5 安全与凭证

API 密钥和访问凭证不得明文存储在普通业务表或日志中。

### 12.6 数据量设计

第一阶段以历史研究数据为主，但应避免只按小规模手工数据设计。

团队需根据预期数据源、频率、历史跨度和原始文件规模选择存储方式。无需过早建设复杂分布式系统，但必须保证历史查询和回放性能可接受。

## 十四、第一阶段开发实施顺序

建议分为五个开发批次。

### P0-1：数据模型与指标字典

交付：

- 数据库核心结构
- 指标字典
- 数据源登记
- 指标与数据源映射
- 时间字段规范
- L5 用途分区字段

验收：能够完整登记一批 L1–L5 指标，字段和约束符合总纲。

### P0-2：原始数据与标准化数据

交付：

- CSV/Excel/JSON 导入
- API 接入基础框架
- 原始数据保存
- 标准化处理
- 数据版本追加
- 基础质量检查

验收：同一指标能够从不同来源接入，且保留原始数据和标准化版本。

### P0-3：研究数据集与分区管理

交付：

- 研究数据集管理
- 数据集版本
- L5 三分区
- 分区冲突检查
- embargo 设置
- 验证区锁定和版本留痕

验收：能够阻止同一研究任务中识别区与验证区出现违规重叠。

### P0-4：历史回放

交付：

- 按 available_time 回放
- 历史版本选择
- 数据快照
- 回放报告
- 数据导出

验收：能够选定历史时点，完整还原当时可获得的数据。

### P0-5：质量与审计

交付：

- 数据质量报告
- 前视偏差审计

- 审计报告

验收：独立审计人员能够完成抽样检查，并得到可复核的结果。

## 十五、开发验收标准

以下是本项目的硬验收条件。

### A. 数据字典

- [ ] L1–L5 指标可以统一登记。
- [ ] 指标基本信息和数据治理字段完整。
- [ ] 每个 L5 指标具备用途政策字段。
- [ ] L5 研究数据集成员具备 usage_partition。
- [ ] 指标定义支持版本化。

### B. 数据接入

- [ ] 支持 CSV、Excel、JSON 导入。
- [ ] 具备 API 接入扩展能力。
- [ ] 原始数据可以追溯。
- [ ] 标准化数据保留来源。
- [ ] 数据修订采用追加方式。

### C. 时间治理

- [ ] 六个核心时间/数据字段完整。
- [ ] 能够区分 observation、release、available、vintage。
- [ ] 能够保留历史版本。
- [ ] 能够识别数据缺失和发布时间延迟。

### D. L5 数据隔离

- [ ] 支持 training、identification、validation。
- [ ] 支持按研究任务登记分区。
- [ ] 能够检查时间窗口重叠。
- [ ] 支持 embargo。
- [ ] 正式验证区使用后不能静默修改分区。
- [ ] 分区变更有完整版本记录。

### E. 历史回放

- [ ] 能够按任意历史时点回放。
- [ ] 只能读取当时已经可用的数据。
- [ ] 能够正确处理历史修订版本。
- [ ] 能够导出回放快照。
- [ ] 相同输入能够复现相同结果。

### F. 审计

- [ ] 支持随机抽样历史时点。
- [ ] 能够核验每条输入数据的 available_time。
- [ ] 能够检查 vintage 版本。
- [ ] 能够生成审计报告。
- [ ] 审计结果可追溯。

### G. 历史不可改写

- [ ] 原始数据不允许原地覆盖。
- [ ] 标准化数据修订采用新版本。
- [ ] 数据集变更创建新版本。
- [ ] 操作记录可查询。
- [ ] 未来实时推断记录具备 append-only 的实现基础。

## 十六、开发团队需要先提交的技术设计

## 十七、第一批测试数据建议

建议开发初期不要一次接入几十个数据源。

先用少量但具有代表性的数据验证系统结构：

- 一项会修订的宏观指标，用于测试 vintage 和 available_time。
- 一项全球金融市场日频指标，用于测试普通时间序列。
- BTC 日线价格，用于测试 L5 观测数据。
- 一项 BTC ETF 资金流数据，用于测试 L4 资金流。
- 一项 BTC 链上指标，用于测试链上数据时间口径。
- 一项 BTC 减半事件，用于测试 known_future_event。
- 一项人为构造的历史修订数据，用于测试历史版本回放。
- 一组人为构造的 L5 训练/识别/验证数据，用于测试分区冲突和 embargo。

先用这些测试数据证明架构正确，再扩大指标范围。
